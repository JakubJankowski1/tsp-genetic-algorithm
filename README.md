# Genetic Algorithm for the Traveling Salesperson Problem

A Python experiment that searches for short tours through TSPLIB city sets. It compares a genetic algorithm with nearest-neighbor and random baselines, records how the population improves, and plots the resulting tours. This repository extracts the working TSP program from a larger university exercises folder.

## How it works

The Traveling Salesperson Problem (TSP) asks for the shortest closed tour that visits each city exactly once. A candidate tour is a permutation of city IDs. For the included experiments, distances use TSPLIB's `EUC_2D` integer rounding; the final edge returns to the starting city.

The genetic algorithm starts with random tours and a few nearest-neighbor tours. Each generation uses tournament selection, ordered crossover (OX), either swap or inversion mutation, and elitism. It stops early after a configured number of generations without improvement. Fixed random seeds make the included runs repeatable. The script also compares parameter settings and reports the distribution from ten runs of the selected setting.

This is a heuristic: it does not guarantee an optimal tour.

## Technology and layout

- Python 3.12, NumPy, pandas, Matplotlib; Python standard library `unittest` for tests.
- [`genetic_algorithms.py`](genetic_algorithms.py): original experiment, parser, baselines, genetic operators, reporting and plots.
- [`run_demo.py`](run_demo.py): one shorter, reproducible `berlin52` demonstration.
- [`prepare_data.py`](prepare_data.py): obtains the benchmark instances from the original TSPLIB site.
- [`tests/`](tests/): deterministic checks of tour scoring, permutation operators and a small GA run.

The program supports the coordinate-based TSPLIB `EUC_2D` instances used here. It is not a general parser for every TSPLIB distance format.

## Windows setup (PowerShell)

Install Python 3.12 and confirm `python --version` prints `Python 3.12.x`, then run these commands from the repository root:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe prepare_data.py
.\.venv\Scripts\python.exe run_demo.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

If `python` selects another version, use the full path to a Python 3.12 interpreter for the first command. For example, on a standard per-user Windows installation: `& "$env:LOCALAPPDATA\Programs\Python\Python312\python.exe" -m venv .venv`. The scripts create `data/` and `outputs/` locally; both are excluded from Git.

The demo prints the length of a valid 52-city tour, the official optimum of 7,542, and the gap. It saves a progress chart and a tour chart to `outputs/`. It does not require an interactive plot window.

To run the complete original experiment on 11, 52, 100 and 150 cities, run it **from `outputs/`** so generated files stay together:

```powershell
New-Item -ItemType Directory -Force outputs | Out-Null
Push-Location outputs
..\.venv\Scripts\python.exe ..\genetic_algorithms.py
Pop-Location
```

The complete experiment runs several configurations plus ten repeat runs, prints extensive progress information, and can take a few minutes. Its output includes PNG charts and CSV summaries. Do not compare older CSV files from the university folder with a new run: some were produced with different distance handling.

## Example results

With Python 3.12.7, the listed dependency versions and the seeds in the scripts, a verified full run produced valid tours with these lengths:

| Instance | GA tour length | Official optimum | Gap |
| --- | ---: | ---: | ---: |
| berlin11_modified (custom subset) | 4,038 | — | — |
| berlin52 | 7,714 | 7,542 | 172 |
| kroA100 | 22,497 | 21,282 | 1,215 |
| kroA150 | 31,349 | 26,524 | 4,825 |

The shorter `run_demo.py` run produced a valid `berlin52` tour of length 8,075. These are observed heuristic results, not promises of optimality. The [kroA100 parameter summary](examples/kroA100_summary.csv) and [progress chart](examples/kroA100_curves.png) were generated by the full run. Its three parameter configurations were compared with a single shared seed; the ten repeats provide a separate view of variability for the selected configuration.

## Benchmark data and attribution

The project uses `berlin52`, `kroA100` and `kroA150` from [Gerhard Reinelt's TSPLIB at Heidelberg University](https://comopt.ifi.uni-heidelberg.de/software/TSPLIB95/tsp/tspindex.html). The [official optimum table](https://comopt.ifi.uni-heidelberg.de/software/TSPLIB95/tsp/TSP-BEST.html) gives 7,542, 21,282 and 26,524 respectively. The TSPLIB [FAQ](https://comopt.ifi.uni-heidelberg.de/software/TSPLIB95/tsp/TSPFAQ.html) explains its integer distance convention. Please cite Reinelt, *TSPLIB—A Traveling Salesman Problem Library*, ORSA Journal on Computing 3(4), 1991.

The original publisher's site does not state a clear permission to redistribute these instance files in this repository. For that reason, no TSPLIB files are committed. `prepare_data.py` downloads the three compressed files directly from the publisher into the ignored `data/` directory. It also creates `berlin11_modified.tsp` locally from the first eleven `berlin52` coordinates; this is a custom subset and has no official TSPLIB optimum.

## Verification and limits

The tests check a known closed-tour distance, validity of crossover/mutation output, and consistency of a small GA result. They do not prove optimality or cover every input and parameter combination. The demo checks that its final tour is a valid permutation and that its reported score matches a fresh calculation. Random seeds help reproduce the results with the stated dependencies, but machine and library differences may affect exact optimization paths.

The code has no web API, database, Docker setup or CI pipeline. It is an algorithmic Python project.
